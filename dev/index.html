TypeAgnosticSerialisation

TypeAgnosticSerialisation serialises an arbitrary Julia value to JSON, YAML, TOML or MessagePack and reconstructs it later without knowing its type up front. The document carries enough type metadata — the full concrete type, including type parameters, recursively — to rebuild the exact concrete type tree. That is what lets a field declared ::AbstractShape come back as the precise Circle{Float64} you put in.

The package itself has no dependencies: it lowers a value to a plain tree and back. Each format is a package extension that activates when you load its backend package (see Formats below).

Type resolution is gated by a module allowlist: a __type__ tag may only name a type defined in a module you explicitly trust, or a plain data type of Base/Core. A named function decodes only if you list it in functions. There is no eval of strings from the document.

Load only documents that you wrote yourself. The allowlists limit what a document can name. They do not make a document from an untrusted source safe to load: the decode builds the types that you allow with the field values that the document gives. Versions before 0.3.0 trusted all of Base and Core and decoded any named function; do not use them for documents that you did not write.

Installation

using Pkg
Pkg.add("TypeAgnosticSerialisation")
Pkg.add("JSON")   # or YAML / MsgPack; TOML is a standard library

A worked example

Everything below is a runnable, tested example. First, a small self-contained set of types. Circle is parametric with a validating inner constructor (radius must be positive); Square is a singleton; Color is an @enum; and Handle wraps a raw pointer — a stand-in for a live, non-data object. Scene ties them together, holding a heterogeneous Vector{AbstractShape}. All the names are exported so they can be used unqualified after using .Shapes. Loading JSON activates the JSON format:

julia> using TypeAgnosticSerialisation

julia> import JSON

julia> module Shapes
           export AbstractShape, Circle, Rect, Square, Color, red, green, blue, Scene, Handle, Doc
           abstract type AbstractShape end
           struct Circle{T} <: AbstractShape
               r::T
               function Circle{T}(r::T) where {T}
                   r > 0 || error("Circle: radius must be positive")
                   return new{T}(r)
               end
           end
           Circle(r::T) where {T} = Circle{T}(r)
           struct Rect{T} <: AbstractShape
               w::T
               h::T
           end
           struct Square <: AbstractShape end
           @enum Color red green blue
           struct Scene
               shapes::Vector{AbstractShape}
               bg::Color
           end
           struct Handle
               ptr::Ptr{Cvoid}
               Handle() = new(C_NULL)
           end
           struct Doc
               title::String
               handle::Handle
           end
       end;

julia> using .Shapes

Serialise and reconstruct

to_json writes a value out; from_json reads it back. The element type of shapes is the abstract AbstractShape, yet each element returns as the exact concrete type it was — that is the whole point:

julia> scene = Scene(AbstractShape[Circle(1.5), Rect(3, 4), Square()], green);

julia> json = to_json(scene; modules = (Shapes,));

julia> back = from_json(json; modules = (Shapes,));

julia> back.shapes[1] isa Circle{Float64}
true

julia> back.shapes[2] isa Rect{Int}
true

julia> (back.shapes[1].r, back.shapes[2].w, back.shapes[2].h)
(1.5, 3, 4)

julia> back.bg === green
true

The modules allowlist limits the types that a tag can name: only types defined in the modules you pass, plus the plain data types and containers of Base/Core (numbers, strings, symbols, arrays, tuples, named tuples, Dict, ranges, …). Hand the same document to a context that does not allow Shapes, and resolution is refused rather than resolving an unexpected type:

julia> try
           from_json(json; modules = ())
       catch
           :refused
       end
:refused

Under the hood, each value is wrapped in a self-describing {"__type__": …, "__value__": …} envelope carrying its full concrete type. For a single Circle(1.5) the JSON reads:

{
  "__type__": {
    "module": "Main.Shapes",
    "name": "Circle",
    "params": [
      { "type": { "module": "Core", "name": "Float64", "params": [] } }
    ]
  },
  "__value__": {
    "r": 1.5
  }
}

Validated vs. direct loading

from_json is validated: every struct is rebuilt through its own constructor, so all inner-constructor / @argcheck invariants run and a tampered or inconsistent document is refused. Circle's constructor requires r > 0; tamper the radius negative and the load fails:

julia> bad = replace(json, "1.5" => "-1.5");

julia> try
           from_json(bad; modules = (Shapes,))
       catch
           :refused
       end
:refused

from_json_direct instead builds each struct field-by-field with Julia's own new, bypassing all constructors. It reconstructs any struct and is still type-safe (new type-checks every field), but runs no user validation — so the same tampered document loads a broken value. Use it for JSON you produced and trust, or for types whose constructor cannot be replayed from its fields:

julia> from_json_direct(bad; modules = (Shapes,)).shapes[1].r
-1.5

Named functions with functions

A field can hold a named function, such as a kernel or a link function. Its type alone states the value, so the document holds no data for it. A named function decodes only if you list it in functions; the default list is empty, so no function decodes:

julia> js = to_json((; kernel = sin));

julia> try
           from_json(js)
       catch
           :refused
       end
:refused

julia> from_json(js; functions = (sin,)).kernel === sin
true

A dict decodes only into Dict or IdDict: the decode calls setindex! on the new dict, and another dict type can act on the system.

Skipping live, non-data fields with opaque

Some fields hold live, non-data objects — open files, solver models, raw pointers — that cannot (and should not) be serialised structurally. Encoding one that is not opted out fails loudly rather than emitting a broken artifact:

julia> doc = Doc("annual report", Handle());

julia> try
           to_json(doc; modules = (Shapes,))
       catch
           :failed_loudly
       end
:failed_loudly

Mark such a type opaque and it is replaced by a placeholder on encode and rebuilt with its no-argument constructor T() on decode. The surrounding data round-trips untouched; the live object comes back fresh:

julia> js = to_json(doc; modules = (Shapes,), opaque = (Handle,));

julia> back = from_json(js; modules = (Shapes,), opaque = (Handle,));

julia> back.title
"annual report"

julia> back.handle.ptr == C_NULL
true

The dependency-free core: encode / decode

to_json is just encode followed by JSON.json. The encode/decode core has no dependencies at all — it lowers a value to a plain tree of Dict{String,Any}, Vector{Any} and scalars, which any text layer can render:

julia> ctx = SerdeContext((Shapes,));

julia> tree = encode(Circle(2.0), ctx);

julia> tree isa Dict{String,Any}
true

julia> decode(tree, ctx).r
2.0

Formats

Every format writes the same plain tree, so every format carries the same type metadata, honours the same modules allowlist and opaque list, and has the same validated / direct pair of loaders. Each one is a package extension: load the backend package and its three functions start working. Until then they fail with a message naming the package to load.

FormatLoad firstWriteRead (validated)Read (direct)
JSONimport JSONto_jsonfrom_jsonfrom_json_direct
YAMLimport YAMLto_yamlfrom_yamlfrom_yaml_direct
TOMLimport TOMLto_tomlfrom_tomlfrom_toml_direct
MessagePackimport MsgPackto_msgpackfrom_msgpackfrom_msgpack_direct

JSON, YAML and TOML produce a String; MessagePack produces compact Vector{UInt8} bytes. The same scene round-trips through each of them:

julia> import YAML, TOML, MsgPack

julia> yaml = to_yaml(scene; modules = Shapes);

julia> from_yaml(yaml; modules = Shapes).shapes[1] isa Circle{Float64}
true

julia> toml = to_toml(scene; modules = Shapes);

julia> from_toml(toml; modules = Shapes).shapes[2] isa Rect{Int}
true

julia> bytes = to_msgpack(scene; modules = Shapes);

julia> bytes isa Vector{UInt8}
true

julia> from_msgpack(bytes; modules = Shapes).bg === green
true

A few format-specific notes:

  • YAML: every string is written quoted, so a string such as "true", "null" or "2024-01-01" is never re-read as another type. A document that uses YAML anchors/aliases is refused: to_yaml never writes them, and an alias lets a tiny document expand into an exponentially large tree.
  • TOML: the top level is always the tagged envelope, so it is always a valid TOML table. Extra keyword arguments (e.g. sorted = true) go to TOML.print.
  • MessagePack: there is no 16-bit float, so a Float16 is stored as the exactly-equal Float32 and narrowed back on load. MessagePack extension values are never deserialised.

CBOR is deliberately not offered: CBOR.jl passes tagged data from the document to Serialization.deserialize, which would let a document build arbitrary Julia objects behind the back of the module allowlist.

Bringing your own format

Because the core is format-agnostic, you can also serialise the plain tree through any other library yourself. When the type is known at the call site (a concrete hint), encode emits a bare structural payload with no envelope — for Rect that is a plain table, which round-trips cleanly through TOML directly:

julia> payload = encode(Rect(3, 4), Rect{Int}, ctx);   # concrete hint -> no envelope

julia> io = IOBuffer(); TOML.print(io, payload); s = String(take!(io));

julia> rt = decode(TOML.parse(s), Rect{Int}, ctx);

julia> (rt.w, rt.h)
(3, 4)

Abstract element types

Containers with an abstract element type round-trip, and every element carries its own concrete type tag. This covers plain abstract types (Vector{Real}, Vector{AbstractShape}), unions (Vector{Union{Missing,Float64}}), partially-applied UnionAlls (Vector{Vector}, Vector{Vector{<:Real}}, Dict{String,Vector}) and Vararg tuples (Vector{Tuple}, Vector{NTuple{N,Int} where N}). The same type descriptors let a value that is such a type (e.g. a field holding Vector{<:Real}) round-trip. Every type named inside a union or a where body is resolved through the module allowlist like any other.

Reserved keys and limitations

The envelope reserves a handful of tree keys: "__type__", "__value__" (the tagged envelope); "type"/"value" (type-parameter wrappers); "union", "where"/"body", "typevar" and "vararg"/"count" (non-DataType type descriptors); "size"/"data" (arrays); "pairs" (dicts); "names"/"values" (named tuples); and "__opaque__" (opaque placeholders). A struct field literally named __type__ would collide — a documented limitation. #undef fields are unsupported and are reported rather than silently dropped.
